# Algorithm Visualization Projects — Regrets Reference Guide

Regression fingerprinting for algorithm visualization web applications (Next.js, React). Covers handling mutable module state, input mutation, non-deterministic randomness, and auto-incrementing IDs.

## The Challenge with Algorithm Visualization Projects

Algorithm visualization projects (sorting visualizers, pathfinding tools, graph algorithm animators) present unique challenges for regression fingerprinting that differ from typical libraries and utilities:

1. **Mutable module-level state** — Many algorithm implementations use `let counter = 0` or `let values = []` at module scope. These counters/accumulators make functions non-idempotent: calling the same function twice produces different IDs or interleaved results.

2. **Functions that mutate their inputs** — Pathfinding algorithms like Dijkstra and A* commonly mutate the grid/node objects passed as input (setting `isVisited`, `distance`, `previousNode`). This means the second call with "the same" input produces wrong results because the input has already been mutated.

3. **Non-deterministic randomness** — Maze generation and random test input creation use `Math.random()`, producing different output on every run. This causes drift detection to fire false positives.

4. **Auto-incrementing IDs** — Node IDs like `"b1"`, `"b2"`, `"u5"` are generated by module-level counters that increment monotonically. Running the same function twice produces different IDs, breaking fingerprint stability.

## Solution: New Manifest Fields

### `resetState` — Reset Module-Level Mutable State

Specify a function name exported by the same module that resets global mutable variables before each capture/validate run:

```json
{
  "id": "bst-insert",
  "entry": "insertActions",
  "watches": ["insertActions"],
  "file": "src/lib/algorithms/bst.js",
  "stack": "js",
  "resetState": "resetCounter",
  "normalize": ["autoIncrement"],
  "inputs": [[5, 3, 7, 1, 4]]
}
```

In the target module, add a reset function:

```js
let counter = 0;
const makeNode = (value) => ({ id: `b${++counter}`, value, left: null, right: null });

// Reset function for Regrets
export function resetCounter() { counter = 0; }

export function insertActions(tree, value) { /* ... */ }
```

**When to use:** Any module that uses `let` or `var` at module scope for counters, accumulators, or caches that affect output.

### `deepCloneInput` — Prevent Input Mutation

When `true` (default), inputs are deep-cloned before each function call so that functions that mutate their input objects don't corrupt test data for subsequent runs:

```json
{
  "id": "dijkstra-path",
  "entry": "dijkstra",
  "watches": ["dijkstra"],
  "file": "src/lib/algorithms/dijkstra.js",
  "stack": "js",
  "deepCloneInput": true,
  "inputs": [{"grid": [[...]], "start": [0,0], "finish": [4,5]}]
}
```

This is enabled by default. Set `deepCloneInput: false` only when you explicitly want the function to see the mutated state from a previous call (rare).

**When to use:** Functions that modify properties of their input arguments (setting `.isVisited`, `.distance`, etc.). This is extremely common in pathfinding and graph algorithms.

### `seed` — Deterministic Random Number Generation

Replace `Math.random()` with a seeded PRNG for the duration of the function call. Uses mulberry32, a fast 32-bit seeded PRNG:

```json
{
  "id": "random-maze",
  "entry": "randomMaze",
  "watches": ["randomMaze"],
  "file": "src/lib/algorithms/randomMaze.js",
  "stack": "js",
  "seed": 42,
  "inputs": [[...grid...]]
}
```

**When to use:** Any function that calls `Math.random()`. Common in maze generation, randomized algorithms, and test input generators.

**Important:** The seed is applied before each function call and restored after. This means:
- All runs produce identical output (no drift)
- The seeded PRNG only affects the function being fingerprinted, not other modules
- The original `Math.random` is always restored, even if the function throws

### `autoIncrement` — Normalize Auto-Incrementing IDs

New normalization rule that replaces sequential ID patterns in output:

```json
{
  "normalize": ["autoIncrement"]
}
```

What it normalizes:
- String IDs: `"b1"` → `"b<ID>"`, `"u5"` → `"u<ID>"`, `"n12"` → `"n<ID>"`
- Numeric IDs: `1` → `"<ID>"`, `42` → `"<ID>"` (integers 1-9999)

**When to use:** When the module uses a counter to generate unique IDs and you want the fingerprint to be stable regardless of how many times the module has been used before the capture.

**Note:** `autoIncrement` normalizes ALL small positive integers (1-9999). If your output contains meaningful small integers (like coordinates, distances, or counts), use `ignoreFields` instead to exclude those specific fields, or combine with `autoIncrement` carefully. Alternatively, use `resetState` to reset the counter so IDs are always deterministic, avoiding the need for `autoIncrement` normalization entirely.

## Recommended Strategy

For algorithm visualization projects, the recommended approach is:

1. **Add `resetState` functions** to each module that uses mutable global state. This is the cleanest solution — it makes functions idempotent without losing information in the fingerprint.

2. **Keep `deepCloneInput: true`** (default) to prevent input mutation from causing false negatives.

3. **Use `seed`** for any function that calls `Math.random()`. This eliminates drift entirely.

4. **Use `autoIncrement`** normalization only when `resetState` alone isn't sufficient (e.g., when IDs are generated by a third-party library you can't modify).

## Adapter Pattern for Next.js

Algorithm visualizers built with Next.js typically use `"noEmit": true` in tsconfig.json. Follow the [Next.js reference](./nextjs.md) for creating adapter modules.

For algorithm visualization specifically:

1. **Extract pure algorithm functions** into adapter files under `regrets/adapters/`
2. **Include reset functions** in the adapters (they don't need to be in the source)
3. **The source of truth is always the original module** — update adapters when source changes

Example adapter:

```js
// regrets/adapters/sorting.js
// Source of truth: src/lib/algorithms/sortingAlgorithms.js

let values = [];

export function resetValues() { values = []; }

export function bubbleSort(arr) {
  values = [];

}
```

## Case Study: AlgorithmVisualizer

A Next.js 15 algorithm visualization app with 24+ algorithms. Key findings during Regrets integration:

- **Mutable globals found in:** mergeSort.js, quickSort.js, heapSort.js (accumulators), linkedList.js (idCounter), bst.js (counter), turing.js (Steps/Maps arrays)
- **Input mutation found in:** dijkstra.js, Astar.js (mutate grid nodes)
- **Non-deterministic functions:** randomMaze.js, recursiveMaze.js (Math.random)
- **Duplicated code between modules:** pathActions (graph.js vs shortestPath.js), helper functions (dijkstra.js vs Astar.js)

All issues resolved using `resetState`, `deepCloneInput`, `seed`, and `autoIncrement` — zero false positives achieved.
