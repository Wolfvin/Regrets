# Kotlin Stack Variant

Regression fingerprinting for Kotlin projects using reflection-based function
invocation and `java`-based capture.

## Status: Community Preview

Kotlin stack support is in **Community Preview** — the core fingerprint
algorithm is implemented (and matches the JS/Python stacks byte-for-byte
on identical inputs/outputs), but the capture/validate flow has the same
manual-setup requirement as the Go stack: you write a manifest, run
`capture_kotlin.sh`, then run `validate_kotlin.sh` after refactoring.
Auto-discovery via `install.js` is not yet wired.

---

## Quick Start

1. Install Kotlin (`kotlinc`) and Java 11+. Either put `kotlinc` on PATH
   or set `KOTLINC_HOME` to the directory containing `bin/kotlinc`.
2. Add `"stack": "kotlin"` clusters to `regrets/manifest.json`.
3. Run `bash scripts/capture_kotlin.sh` to capture fingerprints.
4. Refactor freely.
5. Run `bash scripts/validate_kotlin.sh` to validate.
6. All `.regret` files use the identical format to JS/Python/Go/Rust stacks.

See `proof/kotlin/` for a working example with three clusters.

## Why Kotlin Is Different (vs JS/Python)

| Challenge | JS/Python Approach | Kotlin Reality |
|-----------|-------------------|----------------|
| Function wrapping (ghost proxy) | `Proxy` / decorator | No runtime Proxy — must use reflection on the compiled `.class` |
| Dynamic imports | `import()` / `importlib` | Compile-time only; reflection on `Class.forName()` |
| Module loading | Any file at runtime | Must follow `package` conventions; `Foo.kt` → `FooKt` class |
| Test execution | `node script.js` | Compile with `kotlinc`, run with `java` |
| Top-level functions | Always accessible | Compiled to static methods on a synthetic class (`FooKt`) |
| Method on classes | Wrapped via Proxy | Reflection on instance methods (not yet supported — see Roadmap) |

---

## Equivalent of Ghost Proxy in Kotlin

Kotlin has no runtime Proxy like JavaScript. Instead, we use **reflection
on the compiled class** — the runner loads the user's class via
`Class.forName(fqcn)`, finds the named function as a `Method`, and invokes
it directly. This is sufficient for entry-level fingerprinting (the
function-under-test is the leaf of the call graph).

Callee wrapping (Ghost Proxy for inner function calls) is NOT supported
in this PR — see Roadmap below.

## Manifest Schema

```json
{
  "clusters": [{
    "id": "add",
    "entry": "add",
    "file": "src/Example.kt",
    "kotlinPackage": "regrets.example",
    "stack": "kotlin",
    "fingerprintLevel": "entry",
    "description": "Integer addition",
    "multiArgs": true,
    "inputs": [
      [1, 2],
      [10, 20],
      [0, 0],
      [-5, 7]
    ]
  }]
}
```

### Fields

| Field | Required | Description |
|---|---|---|
| `id` | yes | Cluster identifier (also the `.regret` filename). |
| `entry` | yes | Top-level function name in the source file. |
| `file` | yes | Source file path, relative to the project root. Kotlin puts top-level functions in a synthetic class named `<Filename>Kt` (e.g. `src/Example.kt` → `ExampleKt`). |
| `kotlinPackage` | yes | The `package` declaration at the top of the source file. Combined with `fileClassName`, forms the FQCN: `regrets.example.ExampleKt`. |
| `stack` | yes | Must be `"kotlin"`. |
| `fingerprintLevel` | yes | Currently only `"entry"` is supported (callee-level fingerprinting is on the roadmap). |
| `multiArgs` | no | If `true`, each input is treated as an array of arguments spread across the function's parameters. If `false` (default), each input is a single value passed as the function's sole argument. |
| `inputs` | yes | Array of inputs. Each input is either a single JSON value (when `multiArgs` is false) or an array of values (when `multiArgs` is true). |

### Type Coercion

JSON values from the manifest are coerced to the function's declared
parameter types at invocation time. Supported types:

| JSON type | Kotlin parameter type |
|---|---|
| `number` (integer) | `Int`, `Long`, `Short`, `Byte` |
| `number` (decimal) | `Double`, `Float` |
| `string` | `String` |
| `boolean` | `Boolean` |
| `null` | `null` (nullable parameters only) |
| `array` | `List<*>` |
| `object` | `Map<String, Any?>` |

Custom data classes are NOT yet supported as parameters — see Roadmap.

## The .regret File Format

Identical to the JS/Python stacks. Generated by `capture_kotlin.sh`:

```
cluster: add
version: 1
fingerprint: 63qoext
captured: 2026-06-20T18:02:21.955Z
watches: [add]
entry: add
stack: kotlin
fingerprintLevel: entry
kotlinPackage: regrets.example
fileClassName: ExampleKt
multiArgs: true
env: {"kotlin_version":"...","java_version":"..."}
---
INPUT  [1,2]
OUTPUT 3
HASH   63qoext
```

The fingerprint field is `sha256(stableStringify(input) + "|" + stableStringify(output))`
converted to base36, truncated to 7 characters — the same algorithm as
`scripts/fingerprint.js`. The Kotlin port in `RegretRunner.kt` produces
identical hashes for the same input/output pairs (verified against the JS
reference implementation in the proof-of-concept).

### Multi-input behavior

When a cluster has multiple inputs, the .regret file stores the **first**
input's hash as the golden (`HASH` line). Validation re-runs every input
and reports:

- `RESULT PASS` — the input's hash matches the stored golden (only the
  first input is checked against the golden; subsequent inputs are
  informational because the .regret file format doesn't yet store
  per-input hashes for the Kotlin stack).
- `RESULT INFO` — the input was re-run and its hash computed, but there's
  no stored hash to compare against (inputs 2+ in a multi-input cluster).
- `RESULT FAIL` — the input's hash differs from the stored golden.

This matches the JS stack's `INPUTS` line behavior for inputs 1+. A
follow-up PR can extend the Kotlin capture to write the `INPUTS` line so
all inputs are validated against stored hashes.

## CLI Usage

### Capture

```sh
bash scripts/capture_kotlin.sh
bash scripts/capture_kotlin.sh --cluster add
bash scripts/capture_kotlin.sh --manifest ./regrets/manifest.json
bash scripts/capture_kotlin.sh --quiet
bash scripts/capture_kotlin.sh --verbose
```

Output: one `regrets/<cluster-id>.regret` file per cluster.

### Validate

```sh
bash scripts/validate_kotlin.sh
bash scripts/validate_kotlin.sh --cluster add
bash scripts/validate_kotlin.sh --verbose
```

Exit codes:
- `0` — all clusters PASS (all golden inputs match)
- `1` — at least one cluster FAILed (hash mismatch or runtime error)
- `2` — environment error (kotlinc/java missing, manifest not found)

## Environment Variables

| Variable | Required | Description |
|---|---|---|
| `KOTLINC_HOME` | no | Directory containing `bin/kotlinc`. If unset, `kotlinc` must be on PATH. |
| `JAVA_HOME` | no | Standard JVM variable (read by `kotlinc` and `java`). If unset, `java` must be on PATH. |

## Roadmap (not in this PR)

- **Callee wrapping** (Ghost Proxy for inner function calls) — would require
  compile-time weaving or a custom Kotlin compiler plugin.
- **Method on class instances** — `constructor` + `instanceMethod` pattern
  (matching the Python stack's `classMethod` support). Currently only
  top-level functions are supported.
- **Auto-discovery via `install.js`** — manifest must be hand-written for now.
- **`INPUTS` line for multi-input contracts** — the JS stack writes an
  `INPUTS` line with per-input hashes for inputs 2+. The Kotlin stack
  currently only validates input 0 against the stored golden; inputs 2+ are
  re-run for information only.
- **Custom data class parameters** — currently only primitives, `String`,
  `List`, and `Map` are supported as function parameter types.
- **`regret update`** for Kotlin clusters — the CLI's update flow in
  `scripts/validate.js` doesn't yet dispatch to `capture_kotlin.sh` for
  Kotlin clusters. Run `bash scripts/capture_kotlin.sh --cluster <id>` to
  re-capture manually.
